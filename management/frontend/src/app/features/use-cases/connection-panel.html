Credentials

An API key — what the examples above use. Issued on this page under API keys, shown once, and bound to this use case. Any of the three forms a Gemini client already speaks is accepted, in this order: 

x-goog-api-key: <your key>
Authorization: Bearer <your key>
?key=<your key>

An OIDC token — for a person or a service account, with no key to mint or store. The same header as above; the gateway tells the two apart by their shape. 

Authorization: Bearer <access token>

The token has to reach this use case — through membership, or through a Keycloak group somebody granted it under Members. And it carries no use case, so unlike a key it must name one; that is the section below.

A grant just made takes a few seconds to reach the gateway — configuration travels to the data plane over the event bus, so the console can already show somebody as a member while a request of theirs is still answered 403.

Naming a use case

Usually nothing to do. A key belongs to exactly one use case, so a client holding one sends no use case at all — the request is attributed to the key's own.

A caller who reaches several — an OIDC token, or the unbound break-glass key — has to say which one. There are two ways and they mean the same thing:

A header, when the client can set one: 

X-AIRA-Use-Case: {{ slug() }}

A path prefix, when it cannot — a client that only lets you configure a base URL. /uc/<use-case> goes in front of the whole path; the gateway strips it before routing, so everything after it is exactly the URL above. It works on both surfaces: 

{{ ucExample() }}

Neither grants anything. A selector chooses among the use cases the caller already reaches; naming one they do not is answered 403, not served. Where both are present, the header wins.
