Every model call names its use case, whatever the credential — a key too. The addresses above do it with /uc/{{ slug() }} in front of the path, which the gateway strips before routing. A client that cannot change its path but can set a header sends this instead, to the same address without /uc/{{ slug() }}: 

X-AIRA-Use-Case: {{ slug() }}

A model call that names no use case is refused — 400 on the Gemini API, 403 on the KIRA API — with the prefix to add. Naming one grants nothing: a use case the credential cannot reach is answered 403, and a key names only its own. Where both are sent, the header wins. Reading the model list or what is left of a budget names none.

2 · Who is calling

An API key — for an application, an agent or a script. Issued on this page under API keys, shown once, bound to this use case, and expiring on the date shown there. Any of the three forms a Gemini client already speaks is accepted, in this order: 

x-goog-api-key: <your key>
Authorization: Bearer <your key>
?key=<your key>

The query parameter is Google's convention, and the Gemini API reads it. The KIRA API reads the two headers alone: a key in a URL is written into the log of every proxy it passes, and one sent that way there is refused.

A Keycloak token — for a person or a service account, with no key to mint or store. The same header as above; the gateway tells the two apart by their shape. 

Authorization: Bearer <access token>

The token has to reach this use case — through membership, or through a Keycloak group somebody granted it under Members. It carries no use case, so like a key it names this one through the address.

A grant or a key just made takes a few seconds to reach the gateway — configuration travels to the data plane over the event bus, so the console can already show somebody as a member while a request of theirs is still answered 403.
